# PR Watcher v0

> Historical desktop specification. The authoritative product specification is
> now [`docs/cli/`](cli/README.md). Where the documents conflict, the CLI
> specification wins.

## Goal

Build a local macOS app that watches GitHub pull requests and alerts the user
when either of these things happens for the current PR revision:

- Cursor Bugbot completes its GitHub check.
- A selected Buildkite job completes.

The app must show a blinking menubar icon while it has unread alerts and send a
desktop notification for every new alert.

This is a personal, local app. It polls APIs from the user's machine. Do not
build a server, webhook receiver, account system, or sync service.

## Product scope

### In v0

- Add a GitHub PR by URL.
- Add, edit, pause, and delete rules for an added PR while the app is running.
- Watch the current head SHA, not a PR in the abstract. A new push starts a new
  monitoring cycle.
- Notify once when `Cursor Bugbot` completes for that SHA.
- Notify for selected jobs in a configured Buildkite pipeline.
- Persist PRs, rules, observations, alerts, and settings locally.
- Store GitHub and Buildkite tokens in macOS Keychain.
- Poll every 60 seconds by default, with a manual refresh command.
- Open the PR, Buildkite build, and individual job in the browser from the UI.

### Not in v0

- GitLab, Bitbucket, issues, deploys, or non-PR subjects.
- Webhooks, a hosted backend, push notifications, or mobile support.
- OAuth login, job retries, CI log reading, merge actions, or triggering jobs.
- A general rule language or plugin framework.
- Rich Bugbot finding management. This app reports completion, not findings.

## Sources of truth

Use GitHub to identify the PR revision and its Buildkite build. Use Buildkite
to inspect the individual jobs. Do not try to infer Buildkite jobs from
GitHub's check list: GitHub exposes the pipeline status and build link, not the
jobs inside the build.

For a watched PR `https://github.com/owner/repo/pull/number`:

1. Read `GET /repos/{owner}/{repo}/pulls/{number}` and record `head.sha`.
2. Read `GET /repos/{owner}/{repo}/commits/{head.sha}/check-runs`.
3. Read `GET /repos/{owner}/{repo}/commits/{head.sha}/status`.
4. Find the configured Buildkite status context, parse its `target_url`, then
   call Buildkite for that exact build:
   `GET /v2/organizations/{org}/pipelines/{pipeline}/builds/{number}`.

The Buildkite build request must include jobs. Match rules against the Buildkite
job `name` in v0. Prefer exact names, including punctuation and emoji. We can
add `step_key` matching later, once the desired task list is stable.

  - `status`: `completed`
  - `conclusion`: `neutral`
  - `details_url`: `https://cursor.com/docs/bugbot`
- Buildkite commit-status context: `buildkite/discord-web`

## Configuration

Settings contains:

- GitHub personal access token with read access to the user's private PRs,
  check runs, and commit statuses.
- Buildkite token with `read_builds` permission.
- Poll interval, default 60 seconds; allow 30 to 300 seconds.
- A small list of Buildkite pipeline mappings:

```json
[
  {
    "github_status_context": "buildkite/discord-web",
    "organization": "discord",
    "pipeline": "discord-web",
    "available_job_names": [
      "Web lint",
      "Upload build override"
    ]
  }
]
```

`available_job_names` is a convenience list for the rule picker. The user may
also type an exact job name. The initial values will be supplied by the user
after inspecting a real build.

Tokens go only into Keychain. Do not put them in SQLite, frontend local storage,
logs, diagnostics, test fixtures, or source control.

## Data model

Keep the model small and explicit. SQLite is enough.

```text
watch
  id
  github_owner
  github_repo
  github_pr_number
  title
  active
  created_at

rule
  id
  watch_id
  kind: "cursor_bugbot_completed" | "buildkite_job_completed"
  config_json
  enabled
  created_at

rule_observation
  rule_id
  head_sha
  state: "waiting" | "in_progress" | "completed" | "failed" | "unavailable"
  source_identity
  observed_at

alert
  id
  rule_id
  head_sha
  source_identity
  title
  body
  status: "unread" | "read"
  created_at
```

Use a unique constraint on `(rule_id, head_sha, source_identity)` for alerts.
This is the deduplication guarantee across polls and app restarts.

`source_identity` is the GitHub check-run ID for Bugbot and the Buildkite job
ID for a Buildkite rule. If a selector matches several jobs, use a stable hash
of the sorted job IDs instead.

## Rule behavior

### Cursor Bugbot completed

Configuration:

```json
{ "check_name": "Cursor Bugbot" }
```

For the current head SHA, find the check run with that exact name.

- No matching check run: `waiting`.
- `queued`, `requested`, `waiting`, or `in_progress`: `in_progress`.
- `status == "completed"`: create one alert, regardless of `conclusion`.

The notification must include the conclusion when GitHub supplies one, for
example: `Cursor Bugbot finished — neutral`.

Never alert for a completed Bugbot check merely because the rule was just
created. Record the first observation as a baseline. When the PR later gets a
new head SHA, the existing rule is armed for the new revision and should alert
even if the first poll after that push sees an already-completed check.

### Buildkite job completed

Configuration:

```json
{
  "github_status_context": "buildkite/discord-web",
  "organization": "discord",
  "pipeline": "discord-web",
  "job_name": "Web lint",
  "notify_on": "terminal"
}
```

On every poll, find the newest GitHub commit-status entry for the configured
context. Its target URL must strictly match:

```text
https://buildkite.com/{organization}/{pipeline}/builds/{build_number}
```

If the status or URL is absent, show `waiting`. If it points to the wrong
organization or pipeline, show `unavailable` and expose the error in the UI.
Do not query an arbitrary URL.

Fetch that exact Buildkite build and select all current jobs with an exact
matching `name`.

- No matching job: `waiting` until the build is finished; then `unavailable`.
- Any matching job still runs or queues: `in_progress`.
- All matching jobs are terminal: create one alert.

Treat `passed`, `failed`, `timed_out`, `canceled`, `skipped`, `broken`, and
`expired` as terminal. The alert states the aggregate result:

- all passed: `Web lint passed`;
- any non-passed terminal result: `Web lint finished — failed` (or the best
  available result).

For v0, `notify_on` supports `terminal` and `passed`. Use `terminal` as the UI
default so a failed lint task also gets attention. A `passed` rule does not
create an alert for failure but still shows the failure in the dashboard.

Use only the current Buildkite job attempts returned by the API. Do not attempt
to model job retry history in v0.

## Polling and alert lifecycle

The Rust backend owns polling. It must run while the app window is closed and
the menubar app remains active.

For each active watch:

1. Fetch the current PR head SHA.
2. If this is the rule's first ever observation, save a baseline and emit no
   alert.
3. If the SHA changed, evaluate every enabled rule as a new, armed cycle.
4. Evaluate the sources for that SHA.
5. Insert an alert only if the rule became satisfied and its unique alert does
   not exist.
6. Update the dashboard, tray icon, and unread count.

Network and authentication failures must never make an alert. Show a discreet
`Last poll failed` state with the last useful error and retry on the next cycle.
Do not clear an unread alert when a PR changes or a rule is paused.

## UI and notifications

Use Tauri v2 with a Rust backend and a small React/TypeScript renderer.

### Menubar

- No unread alerts: static icon.
- One or more unread alerts: alternate between normal and attention icons every
  600 ms.
- Menu items: unread alerts, watched PRs, Refresh now, Open dashboard, Quit.
- Clicking an alert opens the dashboard focused on that PR and rule.

### Dashboard

- Empty state explains token setup and has an Add PR button.
- Add PR accepts a GitHub PR URL, validates it, fetches its title and head SHA,
  and lets the user add rules.
- Each PR row shows title, URL, head SHA prefix, last poll, and rule badges.
- Each rule shows `waiting`, `in progress`, `passed`, `failed`, or
  `unavailable`, plus its most recent source link.
- PR detail supports adding rules from configured job names or a typed exact
  job name, pausing a rule, and deleting it.
- Alerts have explicit Read and Mark all read controls.

Opening the app does not mark alerts read. The menubar icon stops blinking only
when every alert is read.

Each new alert sends one native desktop notification. Clicking it should open
the app when platform support allows it; correctness must not depend on that
click behavior.

Keep API clients, rule evaluation, persistence, and tray effects separate.

observations, then returns the next rule state and an optional alert payload.

## Acceptance tests

Write fixture-based unit tests for these cases:

1. The supplied Bugbot fixture (`completed`, `neutral`) creates a completion
   alert, not a success-only alert.
2. A Bugbot check in progress creates no alert.
3. Adding a rule after its source already completed creates no alert.
4. A new head SHA followed by a completed Bugbot check creates exactly one
   alert, including after an app restart.
5. A GitHub status URL resolves the intended Buildkite org, pipeline, and build
   number.
6. A passed matching job creates a passed alert.
7. A failed matching job creates a terminal alert but not a passed-only alert.
8. Parallel matching jobs do not complete until all of them are terminal.
9. A repeated poll creates no duplicate alert.
10. A missing Buildkite status, malformed URL, missing job, API failure, and
    expired token create no notification.
11. Unread alerts start the tray blink; marking the last alert read stops it.

Manually verify on macOS that the app keeps polling after its window closes,
the icon blinks, the desktop notification appears, and the tray Refresh command
updates the dashboard.
